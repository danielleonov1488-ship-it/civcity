### 0.1 Part-based requests and a generic arrow (bug 9, plus the request audit) [Q-9, Q-own-1, K-own-29]

**Root cause** (confirmed by repro, ptr_log.txt):
- hud.gd:2497-2501 picks the arrow target from the request id alone: `_card_or_cat("farming", "warehouse" if g["id"] == "store" else "scriptorium")`.
- «store» is two-part (defs.gd:499, need 2), and its progress is warehouse + butcher (city.gd:1936). The arrow never reads that progress.
- active_goals(1) (city.gd:1941) surfaces «store» only after «village» (defs.gd:497), and Деревня itself needs a warehouse (defs.gd:94). So whenever the arrow shows up, the butcher is the only missing part. The arrow is wrong almost every time.
- Second defect: with nothing researched, the arrow goes to «Хозяйство» instead of «Исследования».
- Third defect: «store» has no `hint` and no `tool`, so clicking its row does nothing (hud.gd:4455-4459).

**Audit of all requests:**
- 12 of the 33 REQUESTS (defs.gd:462-532) have no `hint`: store, artisan, art12, clothes8, floor2x5, temple, school, patrician, floor3, pat10, happy70, forum.
- 7 have neither a hint nor a tool, so clicking them does nothing: store, art12, clothes8, floor2x5, floor3, pat10, happy70.
- `_update_pointer` (hud.gd:2453-2531) is a hand-written match on ids:
  - school, patrician and forum have a tool but no arrow;
  - temple points at the card without checking research (hud.gd:2526);
  - fountain4, happy* and floor2x5 have no arrow at all.

**Design:**
1. **Data.** REQUESTS entries may carry `parts`, an array in the LEVELS `need` shape: `{p, n, text, icon, tool}`.
   - `store` becomes `parts: [{p:["count","warehouse"], n:1, tool:"warehouse", text:"Склад"}, {p:["count","butcher"], n:1, tool:"butcher", text:"Мясная лавка"}]`.
   - Keep `p:["store"]` and `need:2` so `goals_done` and old saves are unchanged. Progress stays computed live.
2. **Resolver.** `Hud._request_target(g) -> {target, tip}`. It takes the first unfinished part, or the whole request when there are no parts, and maps it as follows:
   - **Type:** from `part.tool`, `g.tool`, or `p[1]` when `p[0]=="count"`.
   - **Locked type:** point at the research button. With the research panel open, point at that research card.
   - **Over the rank cap:** `city.cap_err(type) != ""` gives the cap hint as the tip.
   - **Unlocked:** point at the card, or first at its category or tab. commerce goes through the need tab; butcher goes to «Еда».
   - **Floors** (`floors`, floor2x5, floor3): the «Этаж» tool button.
   - **Happiness or coverage:** «Обзор» with the right layer.
   - Hand-written cases stay only for road1 and fam3.
3. **Row UI.** A sub-line under the bar: «Склад ✓ · Мясная лавка 0/1». Clicking the row selects the missing part's tool, or opens research when that part is locked.
4. **Hints.** Write the 12 missing hints in our own words. Example from Q: «Мясная лавка берёт товар со склада — ставьте её в охвате склада (дома и лавки в охвате подсвечиваются)».
5. **Rank checklist rows use the same resolver** (the critique's point; S effort). LEVELS `need` has the request shape, so the rank-button tooltip / station card rows get the same sub-line, click and arrow: Деревня «Склад» → warehouse card or research; «Дома в 2 этажа» → «Этаж» with the 65% hint («дом должен быть полон, счастье не ниже 65%»); Посёлок «Фонтан» → fountain card + «Обзор → Вода»; «Дома ремесленников» → card (or, after 6.8, the upgrade tool). These are exactly the walls testers hit; this is the Хутор-era teaching for the warehouse and floor 2 (D-i, D-p).

**Tests** (test_ux / test_fixes):
- (a) Warehouse built, butcher researched, menu closed → the pointer is on the «Еда» tab or the butcher card.
- (b) Nothing researched → the pointer is on the research button.
- (c) Loop over Defs.REQUESTS: every entry has a hint, and `_request_target` returns a non-null target in a state where the request is open (33/33).
- (d) Clicking the «store» row with the warehouse done selects the butcher tool.
- (e) Warehouse built, butcher **not** researched → the pointer is on the research button; with the research panel open, on the butcher research card.
- (f) Loop over every LEVELS need row of ranks 1–7: the resolver returns a non-null target and a tip in a state where that row is unmet.

**Acceptance:**
- Q's repro_pointer.gd reports the butcher (or research) target.
- 0 requests without a hint; 0 requests where a row click does nothing.
- 0 rank checklist rows without a click target.

**Risk:** low; UI and data only.

### 1.1 Auto quality on first launch [P-8b] (build 31)
- **Who gets it:** only a **new install** (no settings.json at all), or a new install whose adapter name changes later while `quality_user` is not set.
  - Existing installs have settings.json with `"quality": "high"` written by the defaults (game.gd:55, save_settings writes the whole dict), and there is no way to tell a manual «high» from the default. So an existing install **is never re-levelled**: 1.1 writes `quality_auto = "kept"` and only the 1.3 watchdog may *offer* low once. Otherwise the owner's RTX 3060 (table: medium) would drop from high on update, against the promise «ручной выбор никогда не перебивает».
  - The 3050 tester (existing install on high) is covered by the watchdog offer, not by a forced change.
- **(a) Starting level by adapter** (`get_video_adapter_type()` + name):
  - integrated, virtual or CPU device → **very low** (1.2b);
  - GTX 10xx, GTX 16xx, RTX 2050, any RTX 3050, MX, RX 5500 / 6400 / 6500, Arc A3 → low;
  - desktop xx60 class (RTX 2060/3060/4060/5060, RX 6600/7600, Arc A5/A7) → medium;
  - desktop xx70 and up (RTX 2070+/3070+/4070+/5070+, RX 6700+/7700+) → high;
  - the «Laptop» suffix lowers the result **one tier** instead of forcing low: 3060 Laptop → low, 3070/4070 Laptop → medium, 3080/4080 Laptop → high;
  - unknown discrete names → medium.
- **(b) Check on the first entry into the city:** enable `viewport_set_measure_render_time` (0 for about the first 20 frames); skip 60 frames, then the median of `viewport_get_measured_render_time_gpu` over 4 s; above 11 ms, drop one level (only ever down); store `{quality_auto, adapter}`.
- **(c) Never override a manual choice:** a manual pick stores `quality_user = true`; neither (a), (b) nor an adapter change touches it afterwards.
- The advisor says once (per install) which level was chosen and where to change it (owner Q10).
- **Unit tests:**
  - names: «NVIDIA GeForce RTX 3050 Laptop GPU» → low; «NVIDIA GeForce RTX 3060» → medium; «NVIDIA GeForce RTX 3070 Laptop GPU» → medium; «NVIDIA GeForce RTX 4080 Laptop GPU» → high; «Intel(R) Iris(R) Xe Graphics» (integrated) → very low;

- **Expected (GPU side):** a 3050 laptop starts on low at about 38–40 fps in a big city today, and about 60 from the GPU side after 1.2; the CPU limit in big cities is 1.7's job.
